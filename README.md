## 2. Asynchronous Event Processing with Protobuf

**Problem**

Необходимо организовать передачу событий пользовательских сессий между backend-сервисами и системой анализа мошеннической активности.

**Solution**

- Использование Protobuf для компактной сериализации событий.
- Разработка FastAPI endpoint для приёма бинарных сообщений.
- Валидация структуры событий и ограничение размера batch.
- Передача обработанных данных между сервисами.
- Использование асинхронного HTTP-клиента для межсервисного взаимодействия.

**Trade-offs**

- Protobuf vs JSON: производительность, размер сообщений, типизация и удобство отладки.
- HTTP/1.1 vs HTTP/2: сложность инфраструктуры и реальные требования к нагрузке.
- Синхронная обработка запроса vs передача обработки в очередь.
- Строгая валидация схемы vs поддержка динамических данных.

**Challenges**

- Корректная обработка `oneof` полей Protobuf.
- Совместимость при изменении схемы сообщений.
- Ограничение количества событий в одном batch.
- Обработка невалидных бинарных сообщений.

**Result**

Реализован механизм сериализации, валидации и передачи пакетных событий между сервисами. Количественные показатели требуют уточнения.

## 3. Idempotent Batch Processing in MongoDB

**Problem**

Необходимо сохранять пакеты событий в MongoDB, исключая дублирование при повторной доставке запросов и временных сбоях.

**Solution**

- Использование `AsyncMongoClient` из PyMongo.
- Уникальный индекс по `idempotency_key`.
- Пакетная запись через `bulk_write`.
- Использование `UpdateOne` с `upsert=True` и `$setOnInsert`.
- Реализация retry с exponential backoff и jitter.

**Trade-offs**

- `insert_many` vs `bulk_write` с upsert.
- `ordered=True` vs `ordered=False`.
- MongoDB transactions vs операции с идемпотентными ключами.
- Retry на уровне приложения vs retry драйвера.

**Challenges**

- Отсутствие поддержки транзакций на standalone MongoDB.
- Обработка `ServerSelectionTimeoutError` и `ConnectionFailure`.
- Предотвращение дублирования при повторной доставке.
- Корректная обработка частично успешных пакетных операций.

**Result**

Реализована идемпотентная пакетная запись, позволяющая безопасно повторять запросы без создания дубликатов.

**Important:** идемпотентность не гарантирует атомарность всего batch. При частичном сбое часть событий может быть сохранена, а оставшиеся — записаны при повторном запросе.

## 4. Reliability & Retry Mechanisms

**Problem**

Временные сбои внешних сервисов и базы данных могут приводить к неуспешным операциям, повторной доставке данных и увеличению времени ответа.

**Solution**

- Ограничение количества повторных попыток.
- Exponential backoff с jitter.
- Повторная обработка только определённых временных ошибок.
- Настройка таймаутов подключения к базе данных.
- Использование идемпотентности для безопасных повторных операций.

**Trade-offs**

- Fixed delay vs exponential backoff.
- Retry на уровне приложения vs инфраструктуры.
- Быстрое завершение с ошибкой vs дополнительные попытки.
- Retry vs circuit breaker.

**Challenges**

- Предотвращение бесконечных повторных попыток.
- Контроль общей задержки операции.
- Разделение временных и постоянных ошибок.
- Предотвращение перегрузки зависимого сервиса повторными запросами.

**Result**

Реализованы механизмы повторных попыток для отдельных временных ошибок. Влияние на успешность обработки и latency необходимо оценивать по метрикам.

## 5. Performance & High-Load Backend Services

**Problem**

Обеспечение стабильной работы backend-сервисов при увеличении количества одновременных запросов и нагрузки на внешние зависимости.

**Solution**

- Использование асинхронного Python и FastAPI.
- Оптимизация взаимодействия между сервисами.
- Настройка таймаутов и обработки ошибок.
- Тестирование API и анализ поведения под нагрузкой.

**Trade-offs**

- Async I/O vs multiprocessing.
- Увеличение concurrency vs ограничение нагрузки.
- Прямые HTTP-вызовы vs брокер сообщений.
- Производительность vs сложность архитектуры.

**Challenges**

- Поиск узких мест в обработке запросов.
- Контроль количества одновременных операций.
- Работа с медленными внешними зависимостями.
- Обеспечение корректного освобождения ресурсов.

**Result**

_Для конкретных production-проектов необходимо зафиксировать измеримые результаты: RPS, p95/p99 latency, error rate, время обработки и показатели до/после оптимизации._
